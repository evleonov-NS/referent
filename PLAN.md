## План: «О чем статья?» и «Тезисы»

Цель по [PROJECT.md](./PROJECT.md): кратко объяснить содержание статьи и выделить основные тезисы на русском языке.

Ориентир по архитектуре — уже работающий **«Подробный перевод»**: парсинг → отдельный API с промптом → результат в поле «Результат».

### Шаг 1. Зафиксировать промпты в `lib/prompts.ts` ✅ 11.06.2026

Добавить две константы:

- `ARTICLE_SUMMARY_SYSTEM_PROMPT` — краткое описание статьи (3–5 предложений, суть, без воды)
- `ARTICLE_THESES_SYSTEM_PROMPT` — список тезисов (маркированный список, каждый тезис — одна законченная мысль)

Требования к обоим промптам (общие):

- ответ только на русском;
- не выдумывать факты, которых нет в тексте;
- имена, бренды, URL не переводить/не искажать;
- без вступлений и служебных комментариев;
- для тезисов — сохранить нумерованный или маркированный формат списка.

Промпты описать в `PROJECT.md` (раздел «Промпты AI»).

### Шаг 2. Добавить валидацию ответов в `lib/translation.ts` ✅ 11.06.2026

Функции по аналогии с `isInvalidTranslation`:

- `isInvalidSummary(text, sourceLength)` — пустой ответ, `User Safety`, слишком короткий при длинной статье
- `isInvalidTheses(text, sourceLength)` — пустой ответ, нет признаков списка (маркеры `-`, `•`, нумерация)

### Шаг 3. Создать API-эндпоинты ✅ 11.06.2026

**`/api/summarize-article`** (`app/api/summarize-article/route.ts`):

1. Принять `url` / `text` или уже распарсенные `title`, `date`, `content` (как в `translate-article`)
2. Обрезать контент при необходимости (лимит символов)
3. Вызвать `chatCompletion` с `ARTICLE_SUMMARY_SYSTEM_PROMPT`
4. Проверить `isInvalidSummary`; при ошибке — повтор до 3 раз (как в `translate-letter`)
5. Вернуть `{ summary: string }`

**`/api/article-theses`** (`app/api/article-theses/route.ts`):

- Та же схема, промпт `ARTICLE_THESES_SYSTEM_PROMPT`
- Вернуть `{ theses: string }`

User-сообщение (как у перевода):

```
Заголовок: [title]
Дата: [date]

Текст статьи:
[content]
```

### Шаг 4. Подключить кнопки в `ReferentForm.tsx` ✅ 11.06.2026

Изменить `handleArticleAction`:

| Кнопка | Действие |
|---|---|
| `summary` | Парсинг → `/api/summarize-article` → текст в `articleResult` |
| `theses` | Парсинг → `/api/article-theses` → текст в `articleResult` |
| `translation` | Без изменений (уже работает) |

Для `summary` и `theses`:

- статус загрузки: «Текст получен (N символов). Анализ статьи...» / «Выделение тезисов...»
- обратный таймер через `estimateTranslationSeconds` (или отдельные функции `estimateSummarySeconds` / `estimateThesesSeconds`, если нужна другая оценка)
- обработка ошибок в `articleError`

Убрать вывод сырого JSON из поля результата.

### Шаг 5. Оценка времени (опционально) ✅ 11.06.2026

В `lib/translation.ts` при необходимости добавить:

- `estimateSummarySeconds` — короче, чем полный перевод
- `estimateThesesSeconds` — сопоставимо с summary

### Шаг 6. Тесты ✅ 11.06.2026

**Vitest:**

- smoke-тест промптов (константы не пустые)

**Playwright E2E** (без реального AI — мок или только валидация):

- кнопки «О чем статья?» и «Тезисы» при пустом вводе показывают ошибку
- при наличии текста — запрос уходит (можно замокать API позже)

**Smoke API:** `scripts/smoke-api.ps1` — статья [Composer 2.5](https://cursor.com/blog/composer-2-5) + письмо Hoverify.

### Шаг 7. Обновить документацию ✅ 11.06.2026

- `STATUS.md` — перенести задачи из «Не реализовано» в «Готово» с датами
- `PROJECT.md` — добавить промпты для summary и theses
- `README.md` — ссылка на `PLAN.md` (при необходимости)

### Шаг 8. Ручная проверка ✅ 11.06.2026 (URL + письмо)

Проверить на трёх сценариях:

1. URL статьи (например, блог Cursor)
2. Вставленный текст статьи
3. Короткий текст (граничный случай)

Критерии приёмки:

- «О чем статья?» — связный краткий пересказ на русском, без выдуманных фактов
- «Тезисы» — список из 5–10 пунктов, каждый отражает мысль оригинала
- ошибки OpenRouter отображаются понятным сообщением
- результат копируется по клику
